# test_stand
Проект содержит тестовый скрипт `srс/dummy.py` для работы с контроллером 8SMC5-USB без SDK.  
Скрипт работает с драйвером шагового двигателя непосредственно через COM порт.  
Данный скрипт демонстрирует примеры составления и отправки бинарных команд в соответствии с протоколом обмена. 
## Ограничения и предупреждения
Данная инструкция актуальна для ОС Windows. В Linux данный код запустится без внесения изменений, однако нужно уметь получать список подключенных usb устройств самостоятельно, т.к. 
на данный момент (09.06.2025) скрипт не определяет автоматически порт, к которому нужно подключаться. 
После физического подключения драйвера необходимо посмотреть в диспетчере устройств имя COM порта.  
**Внимание!** Скрипт не содержит никаких проверок выхода за диапазон при работе двигателя и не остановит движение, если движущиеся части стенда столкнутся: 
задавая команду на движение следите, чтобы столкновение не произошло.
## Подключение
1. Подключить драйвер 8SMC5-USB к питанию и компьютеру.  
2. Открыть диспетчер устройств и найти драйвер в списке USB устройств.
3. Заменить значение параметра `port` на имя COM порта, соответсвующего устройству в `srс/dummy.py:94`: `prt = Serial(port = "COM3",`.  
## Выбор команды для исполнения
На 09.06.2025 реализованы три команды: `gser`, `movr` и `move` (см. соответствующие функции в скрипте, а также документ `docs/8SMC5-USB.pdf`).  
1. `gser` возвращает серийный номер контроллера, который можно видеть непосредственно на плате (наклейка с цифрами).  
2.  `movr` совершает движение на заданное число шагов (или на заднный угол). Сейчас число шагов захардкожено внутри функции `movr`.  
_Примечание_: что такое шаг и чему он равен устанавливается в настройках. Данный скрипт не предоставляет доступа к настройкам, только пользуется настройками, установленными извне.
3. `move` совершает движение в определенную позицию. Двжиение осуществляется в сторону, противоположную `movr`.
## Запуск
В строке 101 файла `srс/dummy.py` заменить вызов функции на `print(gser(prt))` или `movr(prt)` или `move(prt)` и запустить скрипт `srс/dummy.py` из терминала.
## Что дальше
Использование usb-сниффера во время работы ПО ("из коробки") XILab показало, что при взаимодействии с контроллером ПО постоянно шлет команду получения текущего статуса (приблизительно каждые 100мс, может чаще).
Кроме того в документации говорится о возможном возникновении рассинхронизации между отправялемыми командами и ответами контроллера и приведены способы восстановления синхронности.  
Эти подробности косвенно говорят о рисках взаимодействия с контроллером непосредственно через COM-порт в обход SDK: 
может потребоваться длительная отладка написанного кода в случае реализации сложных сценариев непрерывного движения. Необходимо собрать простой сэмпл на С++ из официальной документации 
и запустить его вместе со сниффером. Если сдк также использует сложные сценарии работы с драйвером, размуно отказаться от работы с контроллером без сдк.  
Однако у данного способа (взаимодействие с двигателем без сдк и из Python) есть свои преимущества: 1) одна и та же кодовая база для всех ОС, на которых можно запустить Python,
2) отстутствие прослойки в виде С библиотек (для каждой ОС -- своего набора библиотек) и отсутствие оберток на Python. Как итог -- простая портируемость на любую платформу и малая кодовая база.
